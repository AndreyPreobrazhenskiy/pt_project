# Network Traffic Analysis: Host Similarity Service

Сервис для анализа сетевого поведения хостов корпоративной сети, кластеризации узлов и поиска похожих компьютеров с объяснением результатов.

## Описание проекта

Проект решает задачу **Network Traffic Analysis (NTA)**: автоматическое выявление типов сетевых узлов (серверы, рабочие станции, подозрительные хосты) и поиск похожих узлов для расследования инцидентов безопасности.

### Ключевые возможности:
- **Кластеризация хостов** по поведенческим признакам (KMeans)
- **Поиск похожих узлов** с использованием косинусного сходства
- **Объяснение результатов** — почему хосты считаются похожими (семантическая оценка ролей)
- **Веб-интерфейс** для удобного анализа (Streamlit)
- **REST API** для интеграции с другими системами (FastAPI)
- **Контейнеризация** для простого развёртывания (Docker)

---

## Архитектура решения

### Система состоит из 4 уровней с микросервисной архитектурой:
**1. Обработка данных (``src/data_processing/extractor.py``)**
Потоковое чтение 1.1 GB сжатых flow-записей с потреблением < 100 MB RAM. Агрегация миллионов строк до 6658 хостов с 6 поведенческими признаками (уникальные хосты/порты, объём трафика, длительность сессий, доля TCP). Результат сохраняется в Parquet (0.12 MB).

**2. Машинное обучение (``src/ml/model_trainer.py``)**
Масштабирование признаков (StandardScaler), кластеризация KMeans (K=6) для выявления типов узлов, построение индекса NearestNeighbors с косинусной метрикой для поиска похожих. Модели сохраняются в models/.

**3. Backend API (``src/api/main.py``, FastAPI, порт 8000)**
Загружает модели при старте, обрабатывает POST-запросы /api/v1/find_similar, возвращает топ-5 похожих хостов с семантическими объяснениями (роль узла, порты, протоколы, длительность сессий). Валидация через Pydantic, автодокументация Swagger на /docs.

**4. Frontend UI (``web_app.py``, Streamlit, порт 8501)**
Веб-интерфейс для аналитиков: ввод ID хоста, таблица результатов, развёрнутые объяснения похожести, статистика по кластерам.
Контейнеризация: Docker Compose оркестрирует два контейнера (API + Web), которые общаются через внутреннюю Docker-сеть. Внешний доступ через проброшенные порты localhost.
Взаимодействие: Пользователь -> Streamlit (8501) -> FastAPI (8000) -> ML-модели -> JSON-ответ -> визуализация.

## Установка и запуск

**Требования:** Docker и Docker Compose

1. Клонируйте репозиторий

```bash
git clone https://github.com/AndreyPreobrazhenskiy/pt_project
cd pt_project
```

2. Скачайте датасет

```bash
wget https://lanl.ma.ic.ac.uk/data/cyber1/flows.txt.gz
```

3. Запустите сервисы

```bash
docker-compose up --build -d
```

4. Откройте в браузере:
    - Web UI: http://localhost:8501
    - API Docs: http://localhost:8000/docs

## Обоснование выбора технологий

Для обработки сырых данных (1.1 ГБ) выбран Polars благодаря его высокой скорости и эффективному управлению памятью: это позволило агрегировать миллионы строк, потребляя менее 100 МБ ОЗУ (ввиду ограниченности ресурсов). В качестве ML-библиотеки использован scikit-learn: алгоритм KMeans отлично подходит для интерпретируемой кластеризации числовых признаков, а NearestNeighbors с косинусной метрикой эффективно находит семантически похожие узлы, фокусируясь на пропорциях трафика, а не на абсолютных значениях.
Бэкенд реализован на FastAPI из-за его высокой производительности, асинхронности и встроенной генерации Swagger-документации. Для фронтенда выбран Streamlit, позволяющий быстро создать интерактивный аналитический интерфейс без написания отдельного JavaScript-кода. Вся инфраструктура упакована в Docker Compose для гарантии воспроизводимости окружения и простоты развертывания одной командой.

## Оценка качества решения

- Достигнутые результаты: Система успешно обработала выборку из 3 млн flow-записей за ~30 секунд, выделив 6658 уникальных хостов. Модель KMeans (K=6) четко разделила сетевую инфраструктуру на интерпретируемые группы (клиенты, серверы, аномалии), а косинусное сходство внутри кластеров стабильно превышает 0.95, что подтверждает корректность поиска.
- Ограничения: Анализ проводился на подвыборке данных; в признаках отсутствуют временные паттерны (активность по часам/дням); KMeans чувствителен к выбросам, хотя в данном случае это помогло выявить подозрительные узлы с аномальным трафиком.
